# @@BRAND@@ API Catalog Architecture

## Source of truth for discovery

API Finder does not bundle a static API list.

Runtime data:

```text
/opt/@@PFX@@/api-catalog/data/catalog.json
/opt/@@PFX@@/api-catalog/data/health-state.json
```

Search interface:

```text
/usr/local/bin/api-catalog-search
```

The catalog is synchronized centrally by @@BRAND@@ administrators. Member containers and Admin Harness receive only the search helper and catalog data as read-only mounts.

## Data flow

```text
public-apis-4Kr upstream
        |
        v
@@BRAND@@ central sync/normalization
        |
        v
catalog.json + health-state.json
        |
        v
api-catalog-search
        |
        v
api-finder
        |
        v
semantic reranking + official verification
```

## Catalog scope

The initial catalog source is `public-apis-4Kr`.

The catalog is a discovery index, not an authoritative registry of every API available in Korea.

Therefore:

- an API being absent does not prove that it does not exist;
- an API being present does not prove that it is currently usable;
- catalog authentication labels are discovery metadata;
- official provider documentation is authoritative for current usage requirements.

## Stable IDs

Entries have a stable @@BRAND@@ catalog ID. When combining results from several queries, deduplicate by `id`, not URL or display name.

## Search score

`score` is a lexical retrieval score generated by `api-catalog-search`.

Use it to retrieve candidates, not as the final semantic ranking.

Final ranking must consider the user's requested capability and context.
