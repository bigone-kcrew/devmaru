01계정 & 첫 로그인

관리자에게 회원 ID를 발급받으면 전용 계정과 개발환경이 함께 준비됩니다. 같은 계정으로 Files와 Windows 네트워크 드라이브도 함께 만들어집니다.

터미널(Windows는 PowerShell)에서 접속합니다.

ssh <ID>@@@SSH_HOST@@ -p @@SSH_PORT@@

<ID>는 발급받은 본인 회원 ID로 바꿉니다. 이 페이지 전체에서 같은 뜻입니다. 맨 위 내 회원 ID에 한 번 입력하면 모든 명령이 내 ID로 바뀝니다.

포트는 @@SSH_PORT@@ 입니다(서버 설정 기준). -p @@SSH_PORT@@ 를 빠뜨리면 다른 포트로 연결됩니다.

첫 로그인에는 개인 이메일로 받은 6자리 초기 비밀번호를 씁니다. 초기 비밀번호는 이메일로만 보내며, 메신저로는 보내지 않습니다.

02비밀번호 변경

가입 시 개인 이메일로 6자리 초기 비밀번호가 발급됩니다. 첫 SSH 로그인에서 새 비밀번호로 변경해야 합니다.

보통 이런 순서로 진행됩니다.

  1. 이메일로 받은 6자리 초기 비밀번호를 입력합니다.
  2. 비밀번호를 바꿔야 한다는 한국어 안내가 먼저 나옵니다. (변경이 필요한 첫 로그인에서만 나옵니다.)
  3. 이어서 SSH · 리눅스가 직접 띄우는 영문 입력 화면이 나옵니다. 아래 세 줄은 원래 영문이며 오류가 아닙니다.
  4. Current password — 방금 쓴 초기 비밀번호를 다시 입력합니다.
  5. New password — 새 비밀번호를 입력합니다.
  6. Retype new password — 같은 값을 한 번 더 입력합니다.
  7. 변경 완료 메시지가 나옵니다.
  8. SSH 연결이 끊깁니다.
  9. 새 비밀번호로 다시 접속합니다.

7번에서 연결이 끊기는 것은 오류가 아니라 정상적인 초기 보안 절차입니다. 비밀번호를 바꾼 뒤 다시 로그인하면 그때부터 정상 사용입니다. 입력하는 동안 화면에 아무 글자도 보이지 않는 것도 정상입니다.

비밀번호는 한 번만 바꾸면 됩니다. SSH에서 비밀번호를 변경하면 Files와 Windows 네트워크 드라이브의 비밀번호도 같은 값으로 자동 변경됩니다. 세 곳에 따로 관리할 비밀번호는 없습니다.

비밀번호는 누구에게도 알려주지 않습니다. 관리자도 회원의 비밀번호를 묻지 않습니다.

03SSH Key 만들기

비밀번호 대신 키로 접속하면 더 안전하고 빠릅니다. Windows PowerShell에서 한 번만 만들면 됩니다.

ssh-keygen -t ed25519 -C "company-pc"

-C 뒤는 이 키가 어느 PC의 것인지 알아보기 위한 메모입니다. company-pc, home-pc, laptop처럼 본인이 구분하기 쉬운 이름을 씁니다.

저장 위치를 물으면 그대로 Enter를 눌러 기본값을 씁니다. 파일 두 개가 만들어집니다. 

$HOME\.ssh\id_ed25519       개인키 (private key)
$HOME\.ssh\id_ed25519.pub   공개키 (public key)

.pub이 붙은 파일만 서버에 등록합니다. 확장자 없는 id_ed25519는 개인키이며, 서버에도 관리자에게도 절대 보내지 않습니다. 자세한 내용은 보안 수칙을 확인하세요.

passphrase는 비워 둬도 되고 설정해도 됩니다. 설정하면 접속할 때마다 입력하게 되는데, OS의 SSH agent를 쓰면 입력 횟수를 줄일 수 있습니다. 서버에서 agent를 대신 설정해 주지는 않습니다.

04공개키 등록 & 지문 확인

만든 공개키를 확인해서 직접 등록합니다.

PowerShell에서 공개키 내용을 확인합니다.

Get-Content $HOME\.ssh\id_ed25519.pub
type $HOME\.ssh\id_ed25519.pub

둘 중 편한 쪽을 쓰면 됩니다. 출력되는 한 줄 전체가 공개키입니다.

공개키 등록 — 회원이 직접 합니다

내 PC의 경로와 개발환경 안의 경로는 다릅니다. @@PFX@@-ssh-key-add가 읽는 파일은 접속해 들어간 개발환경 안의 파일입니다. 내 PC의 $HOME\.ssh\id_ed25519.pub를 대신 찾아 주지 않습니다. 그래서 @@PFX@@-ssh-key-add ~/.ssh/id_ed25519.pub를 그대로 실행하면 개발환경 안의 /home/<ID>/.ssh/id_ed25519.pub를 찾다가 «SSH 공개키 파일을 찾을 수 없습니다»로 끝납니다. 아래 붙여넣기 방식은 파일을 옮기지 않으므로 이 문제가 없습니다.

  • 붙여넣기 권장

    위에서 출력한 공개키 한 줄을 복사해 두고, 개발환경에서 @@PFX@@-ssh-key-add를 인자 없이 실행해 붙여넣습니다. 파일을 옮길 필요가 없습니다.

  • 파일 전송

    공개키 파일을 개발환경으로 먼저 복사한 뒤 그 경로를 넘깁니다. 아래 공개키 파일로 등록하기에 있습니다.

내 PC(PowerShell) — 위 Get-Content 출력의 한 줄 전체를 복사한 상태에서 접속합니다.

ssh <ID>@@@SSH_HOST@@ -p @@SSH_PORT@@

아직 키를 등록하기 전이므로 비밀번호를 묻습니다. 정상입니다.

개발환경 — 인자 없이 실행합니다.

@@PFX@@-ssh-key-add

아래 두 줄이 나오면 복사해 둔 공개키 한 줄을 붙여넣고 Enter를 누릅니다. 

SSH 공개키 한 줄을 붙여넣으세요.
공개키:

등록되면 SSH 키를 등록했습니다: SHA256:…가 나옵니다. 같은 키를 다시 넣으면 이미 등록된 SSH 키입니다: SHA256:…가 나오며 이것도 정상입니다.

개발환경 — 나갑니다.

exit

내 PC(PowerShell) — 다시 접속해서 확인합니다.

ssh <ID>@@@SSH_HOST@@ -p @@SSH_PORT@@

비밀번호를 묻지 않고 바로 들어가면 완료입니다. 계속 비밀번호를 묻는다면 잘 안 될 때를 확인하세요.

개인키는 올리지 않습니다

등록에 쓰는 파일은 .pub으로 끝나는 공개키 하나뿐입니다.

  • id_ed25519.pub — 공개키. 서버에 등록하는 것이 이 파일입니다.
  • id_ed25519 — 개인키. 서버에 올리지 않고 내 PC에만 둡니다. 붙여넣기 방식에서도 붙여넣는 것은 .pub의 내용 한 줄입니다.
공개키 파일로 등록하기 — 대체 방법

공개키 파일을 개발환경으로 먼저 보낸 뒤 그 경로를 넘기는 방식입니다. @@PFX@@-ssh-key-add는 개발환경 안에 실제로 있는 파일만 읽으므로 전송이 먼저입니다.

내 PC(PowerShell) — 공개키 파일을 작업공간으로 보냅니다.

scp -P @@SSH_PORT@@ $HOME\.ssh\id_ed25519.pub <ID>@@@SSH_HOST@@:/workspace/id_ed25519.pub

scp는 대문자 -P, ssh는 소문자 -p로 포트를 지정합니다. 아직 키 등록 전이라 비밀번호를 묻습니다.

내 PC(PowerShell) — 접속합니다.

ssh <ID>@@@SSH_HOST@@ -p @@SSH_PORT@@

개발환경 — 보낸 파일의 경로를 넘겨 등록합니다.

@@PFX@@-ssh-key-add /workspace/id_ed25519.pub

개발환경 — 등록이 끝나면 임시 파일을 지웁니다.

rm /workspace/id_ed25519.pub

/workspace/id_ed25519.pub는 등록용 임시 파일이고, 내 PC의 $HOME\.ssh\id_ed25519.pub와는 다른 파일입니다.

macOS·Linux에서는 경로 표기만 다릅니다.

scp -P @@SSH_PORT@@ ~/.ssh/id_ed25519.pub <ID>@@@SSH_HOST@@:/workspace/id_ed25519.pub

등록된 공개키는 본인 계정의 ~/.ssh/authorized_keys에 들어가며, .ssh와 authorized_keys의 권한도 함께 맞춰집니다. 파일을 직접 편집할 필요는 없습니다.

  • @@PFX@@-ssh-key-add공개키를 붙여넣어 등록합니다.
  • @@PFX@@-ssh-key-add <공개키-파일>개발환경 안의 공개키 파일로 등록합니다.
  • @@PFX@@-ssh-key-list등록된 공개키를 SHA256 지문과 함께 봅니다.
  • @@PFX@@-ssh-key-remove <SHA256:fingerprint>지문으로 지정한 공개키를 삭제합니다.

이 명령들은 공개키(.pub)만 다룹니다. 개인키는 서버에 올리지 않습니다. authorized_keys 파일과 권한을 직접 편집할 필요는 없습니다.

등록할 수 있는 키는 Ed25519와 ECDSA입니다. 예전에 만든 ssh-rsa 키는 받지 않으므로, 그런 키뿐이라면 03단계에서 Ed25519 키를 새로 만들어 등록하세요.

내 키가 맞는지 확인 — SHA256 지문

ssh-keygen -lf $HOME\.ssh\id_ed25519.pub -E sha256

출력되는 SHA256:… 값이 이 공개키의 지문입니다. 여러 PC에서 키를 만들었을 때 어떤 키를 등록하는지 구분하는 용도로 씁니다.

내 개인 키 지문

내가 만든 id_ed25519.pub의 식별값입니다. 위 명령으로 언제든 다시 확인할 수 있습니다.

서버 호스트 키 지문

접속 대상인 @@SSH_HOST@@ 서버 자체의 신원을 확인하는 값입니다. 처음 접속할 때 터미널이 보여 주고 수락 여부를 묻습니다.

이름이 비슷하지만 서로 다른 값입니다. 하나는 나를, 하나는 서버를 식별합니다.

05ssh kunion 설정

긴 접속 명령 대신 ssh kunion 한 줄로 접속하도록 설정합니다.

Windows에서 아래 파일을 열어 내용을 추가합니다.

$HOME\.ssh\config 
Host kunion
    HostName @@SSH_HOST@@
    User <ID>
    Port @@SSH_PORT@@
    IdentityFile ~/.ssh/id_ed25519

<ID>는 본인 회원 ID로 바꿉니다. Windows에서도 IdentityFile에는 ~/.ssh/id_ed25519 표기를 쓸 수 있습니다.

이미 config 파일이 있다면 전체를 덮어쓰지 말고 기존 Host 항목 아래에 위 블록만 덧붙입니다. 파일이 없으면 새로 만듭니다.

Host 뒤의 kunion은 내가 정하는 별명입니다. 이 값을 aiclub이나 work처럼 바꿔 두면 ssh aiclub, ssh work로 접속합니다. HostName·User·Port는 서버가 정한 값이라 그대로 두고, 별명만 바꾸면 됩니다. 이 페이지는 kunion을 예로 씁니다.

서버를 여러 개 쓰고 있다면 별명이 겹치지 않게만 정하세요. 같은 config 파일에 Host 블록을 여러 개 둘 수 있습니다.

등록 전

ssh <ID>@@@SSH_HOST@@ -p @@SSH_PORT@@

매번 비밀번호를 입력합니다.

SSH Key + config 등록 후

ssh kunion

키로 인증되어 바로 개발환경으로 들어갑니다.

06개발환경 입장

로그인하면 자동으로 내 전용 개발환경 안으로 들어갑니다. 따로 실행할 명령은 없습니다.

  1. SSH 로그인 → @@PFX@@-server에서 인증
  2. 인증되면 자동으로 내 전용 개발환경 dev-<ID>로 들어감
  3. 작업 폴더 /workspace에서 일반 bash 셸이 시작됨

@@BRAND@@ Dev Environment

Member
<ID>
Container
dev-<ID>
Workspace
/workspace

개념 정리입니다. 화면에 이대로 출력되지는 않습니다.

프롬프트가 아래 형태면 정상적으로 내 개발환경 안에 들어온 상태입니다.

<ID>@dev-<ID>:/workspace$

tmux는 SSH 로그인 시 자동으로 실행되지 않습니다. 처음 보이는 것은 평범한 bash 셸이며, 그것이 정상입니다. 여러 창을 쓰는 작업 화면이 필요할 때만 08 tmx를 실행합니다.

이 상태에서 claude, codex, agy, paseo를 바로 실행할 수 있습니다. 회원이 컨테이너를 직접 다루거나 별도 명령으로 진입할 필요는 없습니다.

로그인하면 보이는 화면

↑ 전체 순서

터미널을 쓰지 않아도 됩니다. 온보딩 이메일로 받은 연결 링크만 있으면 PC 앱이나 휴대폰에서 바로 시작할 수 있습니다. 오래 걸리는 작업을 자리에서 지켜보지 않아도 되고, 이동 중에도 진행 상황을 확인하고 지시를 이어갈 수 있습니다.

Paseo 원격 연결

서버에서 돌아가는 Agent를 PC 앱이나 휴대폰에서 보고 지시합니다. SSH 창을 닫아도, 접속하지 않아도 작업은 계속됩니다.

번호가 붙은 단계를 거치지 않아도 됩니다. 터미널을 쓰지 않는다면 여기가 시작점입니다.

1. 연결 링크 확인하기

계정과 함께 발송된 개인 온보딩 이메일에 Paseo pairing URL이 들어 있습니다.

링크를 잃어버렸거나 다시 확인하려면, SSH로 접속해 개발환경 셸에서 아래 명령을 실행합니다.

@@PFX@@-paseo-pair

현재 pairing 링크와 QR을 다시 보여 줍니다.

2. 내 기기에 Paseo 설치

  • Windows .exe

    paseo.sh/download에서 설치 파일을 내려받습니다. Intel/x64용과 ARM64용이 따로 있으니 PC에 맞는 쪽을 고릅니다.

  • Apple Mac · iPhone · iPad

    Mac은 같은 페이지에서 .dmg를 내려받습니다 (Apple Silicon용 · Intel용).

    iPhone · iPad는 App Store에서 Paseo를 설치합니다.

  • Android 휴대폰 · 태블릿

    Play 스토어에서 Paseo를 설치합니다.

Linux는 같은 페이지에 AppImage · DEB · RPM이 있습니다. 설치 없이 잠깐 확인만 하려면 브라우저로 app.paseo.sh에 접속해도 됩니다.

3. 연결하기

pairing URL을 복사해서 Paseo 앱의 Pairing Link 입력란에 붙여 넣습니다. PC 앱 · 휴대폰 · 브라우저 모두 같은 방법입니다.

이메일의 링크를 눌러도 Paseo 앱이 자동으로 열리지는 않습니다. 복사해서 앱에 붙여 넣어야 합니다. QR로 연결하고 싶다면 @@PFX@@-paseo-pair로 QR을 다시 확인할 수 있습니다. 터미널에서 QR이 깨져 보이면 pairing 링크를 그대로 쓰면 됩니다.

@@BRAND@@ 안내문은 한국어지만, Paseo 자체가 출력하는 일부 문구는 영문입니다. Paseo 원래 프로그램의 출력이므로 오류가 아닙니다.

연결되면 앱에 dev-<ID>가 보이고, 서버에서 돌고 있는 Claude · Codex · Antigravity를 그대로 이어서 쓸 수 있습니다. 여기서부터는 터미널 없이 앱에서 작업을 지시할 수 있습니다.

4. 앱에서 쓸 Agent 인증하기

Paseo는 Agent를 provider라고 부릅니다. 앱의 Chat 모드에서 provider를 고르려면 그 provider가 개발환경에서 인증되어 있어야 합니다. 인증 전에는 인증을 요구하며 선택되지 않습니다.

인증은 SSH로 개발환경 셸에 들어가 provider마다 한 번씩 하면 됩니다. 회원이 직접 하는 작업이며 관리자에게 요청할 필요가 없습니다.

claude · codex · agy는 그냥 실행하면 처음에 로그인 안내가 나옵니다. 안내를 따라가면 인증이 끝납니다.

Claude · Codex · Antigravity는 모두 터미널에서 한 번 인증하면 됩니다. Antigravity는 개발환경 0.4.28부터 agy 로그인 하나로 Paseo의 Antigravity provider가 준비되고, 예전의 별도 앱용 로그인(@@PFX@@-agy-acp-login)은 0.4.28에서 제거되었습니다.

인증은 영구적이지 않습니다. 시간이 지나면 만료될 수 있습니다(우리 서버에서 Claude는 약 4주 안팎으로 만료되는 것을 확인했습니다). 앱에서 provider가 다시 인증을 요구하거나 claude auth status가 loggedIn: false로 나오면 위와 같은 명령으로 다시 로그인하면 됩니다.

  • Claude Code

    claude를 실행하고 안내를 따릅니다. 바로 로그인만 하려면 claude auth login, 지금 상태는 claude auth status로 확인합니다. 앱에서도 이 인증이 그대로 쓰입니다.

  • Codex

    codex를 실행하고 안내를 따릅니다. 바로 로그인만 하려면 codex login, 지금 상태는 codex login status로 확인합니다. 앱에서도 이 인증이 그대로 쓰입니다.

  • Antigravity

    터미널의 agy 로그인 하나만 하면 됩니다. agy를 실행하고 안내를 따릅니다. 절차는 아래에 따로 적었습니다.

    0.4.28에서 바뀐 점 — 예전의 앱용 로그인 명령 @@PFX@@-agy-acp-login과 별도 앱용 인증 파일은 0.4.28에서 제거되었습니다. 앱에서 Antigravity가 보이지 않으면 터미널에서 agy로 로그인했는지 먼저 확인하세요.

claude
codex
agy

다 쓸 생각이면 다 해 두면 됩니다. 필요한 것만 해도 됩니다.

인증이 끝나면 앱의 설정 → 프로바이더에서 기본으로 쓸 provider를 고릅니다. 주로 쓰는 것 하나만 정해 두면 됩니다.

인증 정보는 회원마다 따로 저장되어 다른 회원과 섞이지 않고, 내 개인 설정 안에 남아 개발환경이 새것으로 바뀌어도 다시 인증하지 않아도 됩니다.

Antigravity 인증 절차(0.4.28) — 서버에는 열 브라우저가 없어서, 주소를 내 PC에서 직접 열고 받은 코드를 터미널에 붙여 넣는 방식입니다.

  1. 터미널에서 agy를 실행합니다(대화형).
  2. 로그인 방식을 물으면 Google OAuth를 고릅니다.
  3. 화면에 출력된 Google 로그인 주소를 내 PC 브라우저에서 열어 Google 계정으로 인증합니다.
  4. 인증이 끝나면 나오는 코드를 복사해 터미널의 입력 칸에 붙여 넣습니다. 일부만 복사하면 실패합니다.
  5. 끝나면 agy models로 쓸 수 있는 모델 목록이 나오는지 확인합니다.

Antigravity가 출력하는 문구는 영문이며 오류가 아닙니다. 다시 하고 싶으면 agy를 한 번 더 실행하면 됩니다. 복사해서 붙여 넣는 주소와 코드에는 내 인증 정보가 들어 있습니다. 비밀번호와 같게 취급하고 누구에게도 보내지 마세요.

Antigravity의 앱(Paseo) 제약 — Paseo에 내장된 Antigravity provider는 Full access 모드 하나뿐입니다. 셸 명령이 권한 확인 없이 실행되므로 믿을 수 있는 작업에만 쓰고, 중요한 작업은 Claude · Codex나 터미널의 agy(권한 확인이 켜져 있음)를 쓰세요. Paseo의 MCP 도구 주입과 중간 개입(steering)은 이 provider에서 지원되지 않습니다 (agy 자체의 MCP 설정은 동작하고, 앱 Chat의 Antigravity에 @@BRAND@@ MCP 도구가 자동으로 붙는지는 아직 확인되지 않았습니다). agy -p(비대화형)는 로그인이 안 되어 있으면 60초 동안 로그인을 기다립니다.

개발환경 0.4.28로 바뀌면 처음 시작할 때 예전 Antigravity 앱용 설정 항목이 자동으로 정리되고 설정 파일의 백업이 만들어집니다. agy 로그인 파일이 없는 회원은 위 절차로 새로 로그인해야 합니다.

5. 파일 다운로드 켜기 (선택)

앱에서 «변경사항» 등의 파일을 받을 때 «다운로드 호스트를 사용할 수 없습니다»라고 나오면 먼저 Paseo 앱을 최신 버전으로 업데이트하세요. 최신 앱은 pairing 링크(릴레이) 연결에서도 64MB 이하 파일을 받을 수 있어서, 따로 켤 것이 없습니다.

64MB를 넘는 파일은 «file too large (64 MB)»라고 나오며 이 방법으로는 받을 수 없습니다. 그런 파일을 앱에서 바로 받아야 할 때만 아래 직접 연결을 관리자에게 요청하세요(관리자가 내 직접 연결 주소를 열어 줘야 합니다). 쓰지 않을 사람은 아무것도 하지 않아도 되고, 기존 pairing 연결은 그대로 쓸 수 있습니다.

1) 서버 쪽 켜기 — 관리자가 준비됐다고 알려 준 뒤에, SSH로 개발환경 셸에 접속해 아래 명령을 실행합니다. 관리자가 열어 주기 전에는 명령을 실행해도 밖에서 연결되지 않습니다.

@@PFX@@-paseo-host on

Paseo 데몬 암호를 한 번 입력합니다(기존 계정 비밀번호와 같아도 됩니다). 이어서 재시작 확인을 묻는데, 재시작하면 실행 중이던 Agent 작업이 끊길 수 있으니 작업이 없을 때 하세요.

2) 앱에서 연결하기

  1. 앱 호스트 화면에서 Add host를 누릅니다.
  2. 직접 연결을 고릅니다.
  3. 호스트에 <내ID>.paseo.@@DOMAIN@@, 포트에 443을 입력하고 SSL 사용에 체크합니다.
  4. 위에서 정한 비밀번호를 입력하고 연결을 누릅니다.

<내ID>는 SSH 아이디와 같습니다. 내 주소는 @@PFX@@-paseo-host status로도 확인합니다. 주소는 앱의 Advanced 입력란이 아니라 위의 호스트·포트 칸에 넣으세요(Advanced 칸에 주소 형식으로 넣으면 앱 오류로 연결이 안 될 수 있습니다). 끄려면 @@PFX@@-paseo-host off를 실행합니다(암호는 남고 직접 연결만 닫힙니다).

알아둘 점 — 직접 연결은 한국 IP에서만 접속됩니다(해외에서는 안 됩니다). 이 암호는 pairing 링크처럼 내 Agent·터미널·파일에 접근하는 자격증명이니 공유하지 마세요. 암호 없이 켤 수는 없습니다. SSH 비밀번호를 바꿔도 이 암호는 자동으로 바뀌지 않으니, 바꾸고 싶으면 @@PFX@@-paseo-host on에서 새로 입력하세요.

왜 개발환경을 새것으로 바꾸나요?

Claude·Codex 같은 AI 프로그램은 자주 새 버전이 나옵니다. 회원마다 하나씩 고쳐 넣는 대신, 최신 프로그램이 담긴 깨끗한 틀을 새로 만들어 갈아 끼우는 방식이 더 빠르고 안전합니다. 사무실의 낡은 PC를 새 PC로 바꾸되 내 문서 폴더는 그대로 옮겨 주는 것과 같습니다.

그래서 회원마다 프로그램 버전이 조금씩 다를 수 있습니다. 작업에는 지장이 없고, 지금 내 버전은 서버 환경의 확인 명령으로 볼 수 있습니다.

개발환경 안에 직접 설치한 프로그램은 틀이 바뀔 때 사라집니다. 자주 쓰는 것이 있으면 관리자에게 요청하세요 — 공통 환경에 넣어 드립니다. 내가 만든 파일은 사라지지 않습니다.

만든 파일을 내 PC로 가져가려면 Files를 이용하세요.

프로젝트 폴더 만들기

새 일을 시작할 때 폴더를 손으로 만들지 않아도 됩니다. 혼자 쓰는 것과 함께 쓰는 것 중에서 고르면 됩니다.

  • 혼자 쓰는 작업공간 기본

    내 작업 폴더 안에 프로젝트 폴더를 만들고 Git 저장소까지 함께 준비합니다. 대부분의 작업은 이것으로 충분합니다.

    @@PFX@@-workspace-create <project>

    <project>에는 프로젝트 이름을 넣습니다 — /workspace/<project>에 만들어집니다. Git 없이 폴더만 만들려면 --no-git을 붙입니다.

  • 공유 작업공간

    여러 회원이 같은 폴더를 함께 쓰는 방식입니다. 같은 파일을 같이 보고 고칠 때 씁니다.

    @@PFX@@-shared-workspace-create <project>

    /shared/workspaces/<project>에 만들어집니다. 여기서도 --no-git을 쓸 수 있습니다.

  • 공유 저장소 + 내 작업 branch

    Git 저장소는 함께 쓰고 작업 공간은 회원별로 나누는 방식입니다. 각자 자기 branch에서 고치고 나중에 합칠 때 씁니다.

    @@PFX@@-shared-worktree-create <project>

    내 작업 폴더는 /shared/worktrees/<project>/<ID>, 내 branch는 users/<ID>로 준비됩니다.

어느 것을 고를지 모르겠으면 첫 번째입니다. 혼자 하는 작업은 @@PFX@@-workspace-create, 같은 파일을 함께 고칠 때는 공유 작업공간, 각자 branch로 나눠 작업하고 합칠 때는 공유 저장소 + 내 작업 branch입니다. Agent에게 «새 프로젝트 만들어줘»라고 말해도 됩니다.

Tool · MCP — 실제 기능

Tool은 실제 REST · MCP · 공용 기능입니다. MCP는 Claude·Codex 같은 Agent가 그 기능을 Tool로 사용하는 연결 방식이며, plugin 목록이 아니라 Agent의 MCP · tool 등록에서 확인하는 대상입니다.

Tools Hub는 사용할 수 있는 기능을 모아 둔 목록(registry)이며, 요청을 대신 처리하는 게이트웨이가 아닙니다. MCP는 각 Agent에 관리형으로 직접 등록되며, 별도의 중앙 MCP Gateway는 사용하지 않습니다. 서비스 규모가 커지면 다시 검토합니다.

  • Kordoc 관리형 MCP

    한글 · HWPX · 공문서를 읽고 작성 · 변환 · 검증하는 기능입니다. PDF · HWP · HWPX와 공문서는 Kordoc이 먼저입니다. 문서 파싱 · 생성 · 편집 · 검증 · 비교 · 개인정보 마스킹까지 여기서 다룹니다.

    중앙 REST 서비스가 원본이고, 회원용 thin MCP가 함께 제공되며, 같은 이름의 Core Skill도 있습니다.

    thin MCP의 도구 이름은 공식 kordoc-mcp와 같습니다 — kordoc_ 접두사가 없습니다(예: parse_document). 이미 열려 있던 세션은 다시 시작해야 새 이름이 보입니다.

    문서 작업은 Agent에게 그대로 요청하면 됩니다. API를 직접 호출할 때만 Kordoc API 문서를 참고합니다. 이 문서 주소는 토큰 없이 열립니다. 토큰은 API를 실제로 호출할 때 필요합니다.

    개발환경 밖의 서버나 개인 PC에서도 같은 중앙 Kordoc을 REST API로 부를 수 있습니다 — Kordoc 외부 API를 보세요.

  • MarkItDown 관리형 MCP

    DOCX · XLSX · PPTX · HTML · TXT 같은 일반 파일을 Markdown으로 변환해 읽어 오는 기능입니다. Kordoc까지 갈 필요가 없는 파일을 빠르게 텍스트로 만들 때 씁니다.

    PDF · HWP · HWPX에는 사용하지 않습니다 — 그건 Kordoc이 먼저입니다. 회원 개발환경의 Claude · Codex에 이미 연결되어 있고, 별도 token이나 header를 입력할 일은 없습니다.

  • Crawl4AI 중앙 API + MCP

    공개 웹 페이지를 받아 오고 사이트 안을 따라가며 탐색하는 중앙 서비스입니다. 주소를 아는 페이지를 가져오는 것뿐 아니라, 같은 사이트의 내부 링크를 따라가며 모을 수 있고 «무엇을 찾는지»를 함께 주면 관련된 페이지를 먼저 봅니다. 조사 · 자료 수집 · 정리와 정기적으로 모으는 수집기의 뒷단으로 씁니다.

    중앙 Crawl API가 원본이고, Claude · Codex에는 얇은 MCP로 함께 등록되어 있습니다. 그래서 Agent에게 그대로 요청해도 되고, 스크립트나 정기 수집기에서 같은 중앙 API를 직접 호출해도 됩니다. 원본 엔진을 직접 다룰 일은 없습니다.

    인터넷 전체를 검색하지는 않습니다 — 지정한 사이트 안을 따라가는 탐색은 되지만, 어떤 사이트를 볼지 고르는 것은 Agent나 회원입니다. 로그인 · 클릭 · 폼 입력 같은 조작도 하지 않습니다 — 그건 아래 agent-browser Skill이 합니다. 회원이 token을 알거나 설정할 일은 없습니다.

  • Korean Law 관리형 MCP

전역지침이란?

Agent에게 매번 다시 말하지 않아도 되도록, 모든 작업에 공통으로 적용되는 기본값을 적어 둔 파일입니다. 답변 언어, 어디까지 확인하고 시작할지, 어떤 작업 전에 물어볼지, 끝났다고 말하기 전에 무엇을 검증할지 같은 것이 여기서 정해집니다.

프로젝트 하나에만 필요한 규칙은 이 파일에 넣지 않고, 그 프로젝트에서 따로 만듭니다. 작업 폴더마다 자동으로 만들어 두지는 않습니다.

두 파일이 각각 어디에 적용되나

  • Claude Code

    CLAUDE.md가 모든 Claude 작업의 기본값이 됩니다. Claude가 읽어 가는 위치는 ~/.claude/CLAUDE.md이고, 내용이 들어 있는 실제 파일은 ~/.@@PFX@@/agent-config/CLAUDE.md입니다.

  • Codex

    AGENTS.md가 모든 Codex 작업의 기본값이 됩니다. Codex가 읽어 가는 위치는 ~/.codex/AGENTS.md이고, 내용이 들어 있는 실제 파일은 ~/.@@PFX@@/agent-config/AGENTS.md입니다.

  • 내가 고칠 파일 그대로 유지

    두 파일 모두 ~/.@@PFX@@/agent-config/ 안에 있습니다. 평소 쓰는 편집기로 열어 고치면 다음 작업부터 반영됩니다.

    이 폴더는 개발환경 바깥에 있어서, 개발환경이 새것으로 바뀌어도 내가 고친 내용은 그대로 남습니다.

이 파일은 보안 경계가 아닙니다. 조직이 강제하는 보안정책이 아니라, 회원이 수정할 수 있는 작업 기본값입니다. 실제로 무엇을 할 수 있는지는 시스템 권한과 플랫폼 통제가 정합니다. 그리고 비밀번호 · API key · 토큰 · 개인키는 이 파일에 적지 않습니다 — 보안 수칙과 같습니다.

## Publishing Websites and Apps

* Publishing is public. Before creating `<project>/publish/` or running `@@PFX@@-app publish`, tell the user what will become public (including that there is no login) and get explicit confirmation.
* Never put secrets, keys, tokens, `.env` files, personal data, or symlinks in `publish/`, app code, compose files, or logs. Do not publish a development server, debug mode, or an unauthenticated admin page.
* Static files go in `<project>/publish/` (run `@@PFX@@-site check <project>` first and report every finding). Edits go live at once, a new folder within a minute; `publish/` itself must not be a link. A project under `/shared/workspaces` is published automatically at `https://@@PORTAL_HOST@@/<project>/`. Server apps (Django, FastAPI, Node, ...) use `@@PFX@@-app publish <app> <port> [--dir <app-folder>] [--basic] [--days N] [--start "<command>"]`; no administrator approval is needed. Both are reachable from Korean IPs only; from inside the server the public URL `https://<app>.@@DOMAIN@@` also works (if blocked, see the local-check section of the `@@PFX@@-publish` skill).
* Layout: project source in `/workspace/<project>`, a server app in `app/`, secrets and personal data in `.private/`; `$HOME` is for tools and login only. Collaborate in `/shared/workspaces`, but never keep a shared app's secrets in `/shared`.
* Behind the proxy, trust `X-Forwarded-For` (rightmost value) and `X-Forwarded-Proto` only when the TCP peer is the server proxy address shown by `@@PFX@@-app ports`; otherwise use the peer address, and never trust `X-Real-IP`, `Forwarded`, or `True-Client-IP`.
* Other containers can reach app ports directly (the Korean-IP limit and `--basic` do not apply), so protect sensitive screens with app login.
* PostgreSQL: each member has one database. Check it with `@@PFX@@-app db status`, give every app its own schema (`@@PFX@@-app db schema <app>`), never use `public` for app tables, and keep the password only in `~/.pgpass`.
* Limits and ports are shown by `@@PFX@@-app ports`. A long-running production service needs the administrator to mark it an operating app (no expiry); do not work around expiry.
* Read the `@@PFX@@-publish` skill for the procedure, limits, and troubleshooting before doing any of this.

Windows 네트워크 드라이브 사용 가능

Windows 11 탐색기에서 개인 작업공간과 공용 폴더를 드라이브처럼 씁니다. Windows 10이면 Files를 쓰세요.

Windows 탐색기에서 개인 작업공간과 공용 폴더를 드라이브처럼 쓰는 방법입니다. SMB over QUIC로 연결하며, 외부 Windows 11 PC에서 연결 · 인증 · 개인 공유 · 공용 공유 · 드라이브 매핑까지 확인을 마쳤습니다.

Windows 11 (24H2 이상)에서만 됩니다. Windows 10에는 SMB over QUIC 클라이언트가 없어 이 방법을 쓸 수 없습니다. 회사 PC가 Windows 10이면 Files를 사용하세요 — 같은 파일을 브라우저에서 올리고 내려받을 수 있습니다.

쉬운 방법: 연결 파일 받기 (smb-connect.bat) — 내려받아 더블클릭하면 회원 ID · 드라이브 문자 · 비밀번호만 입력해 내 폴더가 연결됩니다. 공용 폴더(shared)도 같이 연결하려면 두 번째 드라이브 문자를 입력하세요(비워 두면 건너뜁니다). 아래 명령을 직접 입력하는 것과 같은 일을 하고, 비밀번호는 파일에 들어 있지 않습니다. Windows가 경고를 띄울 수 있으며, 파일 내용은 메모장으로 열어 확인할 수 있습니다.

직접 명령으로 하려면 아래 순서를 따르세요.

1. 비밀번호를 한 번 저장합니다. 일반 PowerShell(관리자 권한 불필요)에서 실행하면 비밀번호를 입력창에서 묻습니다. 비밀번호는 지금 쓰는 SSH 비밀번호와 같고, 저장해 두면 재부팅해도 다시 묻지 않습니다.

cmdkey /add:@@SMB_HOST@@ /user:<ID> /pass

2. 내 개인 폴더를 X: 드라이브로 연결합니다. 이미 쓰는 문자라면 다른 문자(예: L:)로 바꾸세요.

New-SmbMapping `
  -LocalPath 'X:' `
  -RemotePath '\\@@SMB_HOST@@\<ID>' `
  -TransportType QUIC `
  -QuicPort 1443 `
  -Persistent $true

3. (선택) 공용 폴더를 Y: 드라이브로 연결합니다.

New-SmbMapping `
  -LocalPath 'Y:' `
  -RemotePath '\\@@SMB_HOST@@\shared' `
  -TransportType QUIC `
  -QuicPort 1443 `
  -Persistent $true

확인한 범위: 외부 Windows 11 PC 1대에서 위 순서로 연결하고, 재부팅한 뒤 비밀번호 입력 없이 다시 연결되는 것까지 확인했습니다. 다른 PC에서 문제가 있으면 오류 문구를 관리자에게 알려 주세요.

  • 내 폴더 개인

    \\@@SMB_HOST@@\<ID> — 나만 쓰는 공간입니다.

  • 공용 폴더 공유

    \\@@SMB_HOST@@\shared — @@BRAND@@ 공용 작업공간입니다. 다른 회원도 함께 봅니다.

  • 드라이브가 안 보일 때

    명령은 성공했고 Get-SmbMapping에도 보이는데 탐색기 「내 PC」에만 나타나지 않는 경우가 있습니다. 탐색기를 다시 시작하면 표시됩니다. 

    taskkill /f /im explorer.exe
start explorer.exe

  • 재부팅 뒤 «연결 끊김»으로 보일 때

    재부팅 직후에는 드라이브가 «연결 끊김»(탐색기에는 빨간 X)으로 보일 수 있습니다. 드라이브를 한 번 열면 비밀번호 없이 다시 연결됩니다. 연결 상태는 Get-SmbMapping으로 볼 수 있습니다.

  • 오류가 날 때

    «로컬 장치 이름에 저장된 다른 네트워크 리소스에 대한 연결이 있습니다» — 이미 쓰는 드라이브 문자입니다. 다른 문자로 바꾸세요.
    «매개 변수가 틀립니다» — 명령에 -SaveCredentials를 넣지 마세요. 비밀번호 저장은 위 1번 cmdkey로 합니다.
    «네트워크 경로를 찾지 못했습니다» — 한 번 나왔다가 다시 하면 되는 경우가 있었습니다. 계속 나오면 UDP 1443이 막힌 망인지 확인하세요(아래 «회사망에서 막힐 때»).

  • 비밀번호를 바꿨을 때

    서버 비밀번호를 바꾸면 PC에 저장된 값이 낡아 연결이 실패합니다. 1번 cmdkey 명령을 같은 이름으로 다시 실행해 새 비밀번호를 저장하세요.

  • 연결 끊기

    더 쓰지 않을 때는 드라이브 문자로 해제합니다.

    Remove-SmbMapping -LocalPath 'X:' -Force

  • 회사망에서 막힐 때

    이 방식은 UDP 1443을 사용합니다. 회사 네트워크에서 막혀 있으면 Files로 파일을 주고받으세요.

5 · 웹 공개 · 프로젝트 서버 약 12분

웹으로 공개하기 — 정적 · 서버 앱 · DB

내가 만든 페이지나 앱을 인터넷 주소로 여는 방법입니다. 한국 IP에서만 열리고, 관리자 승인은 필요 없습니다(규칙은 자동 검사). Agent에게 맡기면 아래 명령은 Agent가 실행하니, 터미널을 쓰지 않아도 됩니다.

  • 정적 웹페이지 (HTML · CSS · JS)

    폴더만 만들면 최대 1분 안에 공개되고, 수정은 바로 반영됩니다.

    <ID>.@@DOMAIN@@/<프로젝트>/
  • 서버 앱 (Django · Flask · FastAPI · Node …)

    앱을 띄우고 @@PFX@@-app publish 로 요청합니다.

    <앱 이름>.@@DOMAIN@@
  • 내 PostgreSQL

    서버 앱이 데이터를 저장할 때. 관리자가 발급합니다.

    @@PFX@@-app db
  • 그 밖의 서비스 · MCP · 사용자 지정 주소

    관리자 요청 절차를 따릅니다.

    프로젝트 서버 사용

정적 웹페이지 — 폴더만 만들면 공개

  • 폴더 만들기

    작업공간(/workspace)에 <프로젝트>/publish/ 폴더를 만들고 index.html 등을 넣습니다. 서버 앱 소스는 app/, 비밀·개인정보는 .private/ 에 두며 publish/ 에는 공개할 파일만 둡니다.

  • 주소

    새 프로젝트 폴더는 최대 1분 안에 https://<ID>.@@DOMAIN@@/<프로젝트>/ 로 열립니다. 이미 열린 프로젝트의 파일을 고치면 바로 반영되고, publish/ 폴더를 지웠다 다시 만들면 다시 최대 1분이 걸립니다. 검색엔진에는 노출하지 않도록 표시됩니다.

  • 공용 페이지

    멤버가 함께 쓰는 /shared/workspaces/<프로젝트>/publish/ 는 https://@@PORTAL_HOST@@/<프로젝트>/ 로 열립니다(허용 IP 만). 관리자 승인 없이 규칙을 만족하면 공개되고 관리자는 사후에 확인합니다: 이름은 소문자로 시작하는 영문 소문자·숫자·하이픈 2~31자, 예약된 이름 제외, publish/ 는 실제 폴더(링크 불가), 폴더 소유자가 현재 멤버, 공용 페이지는 최대 10개. 끄려면 @@PFX@@-site off <폴더>(또는 프로젝트 폴더에 .publish-off), 소유자 계정이 삭제되면 내려갑니다. 공용 폴더에는 비밀을 두지 않습니다(멤버 전원이 읽을 수 있습니다).

  • Agent에게

    예: «kised 프로젝트 결과를 웹으로 공개해 줘». Agent는 공개하기 전에 무엇이 공개되는지 먼저 물어봅니다.

  • 주의

    publish/ 에는 비밀번호·키·.env·개인정보·바로가기(링크)를 두지 않습니다. HTML 안의 경로는 상대경로(css/a.css)로 씁니다. /css/a.css 처럼 /로 시작하면 열리지 않습니다. publish/ 폴더 자체를 바로가기(링크)로 만들면 공개되지 않고, 점(.)으로 시작하는 파일과 비밀처럼 보이는 이름(.env · *.key · *secret* · *token* · *.sqlite · *.sql 등)은 서버가 열어 주지 않습니다. 그래도 그런 파일은 두지 않습니다.

  • 점검·중지

    @@PFX@@-site init <프로젝트> 바로 공개(폴더 만들기와 같음) · @@PFX@@-site check <프로젝트> 공개 전 점검 · @@PFX@@-site list 공개 목록(내 것과 공용) · @@PFX@@-site off <프로젝트> 공개 중지 — 내 것인지 공용인지는 폴더 경로로 판별하므로 같은 이름이 둘 다 있으면 폴더 경로(/shared/workspaces/<프로젝트>)로 알려 줍니다

서버 앱 — @@PFX@@-app

Django 같은 서버 앱은 내 개발 컨테이너 안에서 실행하고, 주소만 열어 줍니다.

  • 파일 위치

    소스·가상환경은 /workspace/<프로젝트>/app/(앱이 여럿이면 app/<앱 이름>/, 가상환경은 app/.venv), 비밀·개인정보는 /workspace/<프로젝트>/.private/ 에 둡니다. publish/ 는 정적 페이지 전용이라 서버 앱은 쓰지 않습니다. 공용 프로젝트의 앱이라도 비밀은 /shared 가 아니라 앱을 공개하는 멤버의 개인 .private/ 에 둡니다. 도구로 새로 만든 프로젝트에는 .private/ 가 미리 들어 있고 다른 멤버는 접근하지 못합니다(직접 만든 폴더에는 없을 수 있으니 직접 만듭니다. 관리자의 프로젝트 폴더 접근은 도구를 고치는 0.5.4 전까지 제한될 수 있습니다).

  • 1. 맡기기

    Agent에게 «이 앱을 웹으로 공개해 줘»라고 합니다. Agent는 공개 전에 로그인 없이 누구나 볼 수 있는지 먼저 확인합니다.

  • 2. 앱 실행

    앱은 내 포트(범위는 @@PFX@@-app ports)에서 0.0.0.0 으로 떠 있어야 합니다. 내 컨테이너 안(localhost)에서만 들으면 열리지 않습니다.

  • 3. 공개 요청

    @@PFX@@-app publish <앱 이름> <포트> --dir <앱 폴더> --start "<시작 명령>"

    1분 안에 https://<앱 이름>.@@DOMAIN@@ 로 열립니다. 로그인이 필요하면 --basic 을, 기본 30일 대신 기간을 정하려면 --days N(최대 365)을 더합니다. 결과는 @@PFX@@-app status <앱 이름>. --dir 은 앱 소스 폴더(/workspace/<프로젝트>/app 아래)로, 서버가 앱과 프로젝트의 연결을 기록하고 --start 를 그 폴더에서 실행합니다. 생략하면 현재 폴더가 app/ 아래일 때 그 폴더를 씁니다.

  • 규칙

    이름은 소문자로 시작하는 영문 소문자·숫자·하이픈 2~31자이고, 예약된 이름과 다른 멤버가 쓰는 이름은 쓸 수 없습니다. 멤버당 최대 5개, 기본 30일 뒤 만료(@@PFX@@-app renew, 최대 365일 — 만료 14일 전에 관리자에게 알림이 갑니다), 요청 본문 10MB 제한입니다. 오래 운영할 서비스는 관리자에게 «운영 앱» 지정(만료 없음)을 요청하세요. 어기면 거부 사유가 @@PFX@@-app status 에 나옵니다.

  • 관리

    @@PFX@@-app list 목록 · @@PFX@@-app log <앱 이름> 로그 · @@PFX@@-app renew <앱 이름> [--days N] 연장 · @@PFX@@-app password <앱 이름> --basic 로그인 정보 · @@PFX@@-app off <앱 이름> 중지(앱 프로세스는 직접 종료)

  • 컨테이너가 다시 만들어지면

    앱 프로세스가 꺼집니다. --start 에 시작 명령을 등록해 두면 서버가 앱이 꺼져 있을 때 그 명령으로 다시 시작합니다.

  • 시작 골격

    @@PFX@@-app template django|fastapi|node [폴더] 로 공개용 설정이 들어 있는 시작 골격을 만듭니다(폴더를 생략하면 현재 프로젝트의 app/, 비밀 키·환경 파일은 프로젝트의 .private/ 를 씁니다). Flask 등 다른 프레임워크도 포트와 시작 명령만 맞으면 됩니다.

로그인이 없으면 한국 IP 누구나 접속합니다. 개발 서버(runserver·reload)와 디버그 모드는 공개하지 않습니다. 개인 정보나 관리자 화면이 있는 앱은 --basic 이나 앱 자체 로그인을 씁니다. Agent도 같은 규칙을 지침으로 받습니다.

내 PostgreSQL

  • 발급

    새 멤버는 계정을 만들 때 자동으로 발급됩니다. 기존 멤버는 관리자가 한 번 만들어 줍니다(이후 앱을 늘릴 때는 승인이 필요 없습니다). 발급되면 내 컨테이너의 ~/.pgpass 에 접속 정보가 들어가며, 암호는 화면에 나오지 않고 Agent도 알 필요가 없습니다. 이미 DB가 있는 멤버는 접속 정보 재설정을 요청합니다.

  • 확인·연결

    @@PFX@@-app db status 로 연결을 확인하고(직접 SQL은 @@PFX@@-app db psql), @@PFX@@-app db dsn 이 알려 주는 호스트·DB·사용자 이름만 앱 설정에 씁니다. 암호는 ~/.pgpass 에서 읽게 합니다(Django 시작 골격은 이미 그렇게 되어 있습니다).

  • 여러 앱이 쓸 때

    DB는 멤버당 하나(<ID>_db)이고, 앱마다 스키마를 나눠 씁니다. @@PFX@@-app db schema <앱 이름> 으로 만들면 테이블 이름이 앱별로 따로라 겹치지 않습니다(예: blog.users, shop.users). 앱 설정에는 DB_SCHEMA=<앱 이름>(Django 시작 골격이 적용)이나 search_path 로 알려 줍니다. 앱은 모두 내 계정 하나로 접속하므로 권한까지 나뉘지는 않습니다(앱 전용 계정은 이후 단계).

  • 백업

    @@PFX@@-app db backup 은 /workspace/.db-backups 에 최근 7개를 남깁니다. 멤버 DB는 서버 백업에 포함되지 않습니다. 중요하면 이 백업을 따로 보관하세요.

  • 규칙

    연결은 20개까지, 내 DB 밖과 다른 멤버 DB에는 접속할 수 없습니다. 비밀번호는 코드·.env·compose·로그에 쓰지 않습니다.

질문 3개로 관리자에게 부탁할 것이 있는지 알려 드립니다. 권한이 자동으로 생기지는 않습니다.

프로젝트 서버 사용

↑ 맨 위

기존 회원도 새 프로젝트를 시작할 때 SSH·실행환경·PostgreSQL 범위를 관리자에게 요청할 수 있습니다. 회원 Agent는 멤버 계정의 권한만 사용하며 서버 전체 권한을 받지 않습니다.

  • SSH — 지금 쓰는 키를 그대로 사용

    이미 등록한 SHA 공개키로 접속합니다. Claude Code나 Codex가 작업할 때도 같은 멤버 계정으로 접속합니다.

    ssh -p @@SSH_PORT@@ <내 ID>@@@SSH_HOST@@

    개인키는 Agent·채팅·서버에 복사하지 않습니다. 키 추가·교체·폐기는 관리자에게 요청합니다.

    Agent의 SSH 명령·host key 확인·원격 파일 전송 예시는 공통 작업 지침(MD)를 먼저 읽습니다.

  • 프로젝트 실행환경 — 관리자 승인 범위

    프로젝트 실행환경은 멤버별로 분리해 준비합니다. 서버 전체 관리 권한이나 sudo 권한은 열지 않습니다. 현재는 서버 전체 컨테이너 관리 권한이나 임의 서비스 실행 권한을 제공하지 않으며, 멤버별 프로젝트 실행환경은 staging 검증을 완료했습니다. 다른 멤버는 별도 승인 후 적용합니다.

    여러 프로젝트를 운영할 수 있지만, 각 프로젝트의 작업공간·연결 주소·자원 한도는 관리자 승인 범위 안에 둡니다.

    운영용 host loopback port는 멤버가 임의 확정하지 않습니다. 요청서에 loopback_port: admin-assigned를 적으면 관리자가 충돌을 확인하고 host loopback 전용 포트를 배정합니다.

  • 웹 페이지·서버 앱·내 DB

    정적 페이지와 서버 앱 공개(@@PFX@@-app)는 관리자 요청 없이 위 절 «웹으로 공개하기»의 방법으로 합니다. 내 PostgreSQL은 새 멤버라면 계정을 만들 때 자동으로 발급되고(기존 멤버는 관리자가 한 번), 그 뒤 앱을 늘릴 때는 승인이 필요 없습니다.

  • 공개 API/MCP — 관리자 승인

    사용자 지정 주소나 상시 서비스처럼 위 방법으로 안 되는 공개는 멤버가 서버 설정을 직접 수정하지 않고 서비스명·연결 주소·health 경로·인증 방식을 제출합니다. REST는 @@API_HOST@@, MCP는 @@MCP_HOST@@ 경계를 사용합니다.

    Caddy 설정은 직접 바꾸지 않고 서비스명·경로·upstream·health·인증·만료일을 적은 요청서로 제출합니다.

프로젝트 전용 비밀값 — 멤버 소유 .env

멤버 rootless 프로젝트는 프로젝트 폴더의 .env를 env_file로 주입할 수 있습니다. umask 077로 만든 뒤 chmod 600 .env를 적용하고, .gitignore에 .env를 넣습니다. .env.example에는 변수명만 둡니다. Agent가 읽을 수 있으므로 Agent에게 보여도 되는 값만 넣고, 다른 회원·중앙 서비스 secret은 넣지 않습니다. 관리자 운영 서비스로 승격할 때는 관리자가 별도 secret 경로로 이전합니다. DB 비밀번호는 .env를 포함해 어떤 파일·compose·코드·문서·git·로그에도 두지 않고, PGPASSWORD 환경변수 또는 ~/.pgpass(chmod 600)만 씁니다.

Agent에게 맡길 프로젝트 준비

↑ 맨 위

Agent에게 먼저 프로젝트 폴더를 읽고 아래 제출 패키지를 만들게 하세요. Agent는 코드를 작성·검증할 수 있지만 서버 권한을 늘리거나 Caddy를 직접 바꾸지는 않습니다.

멤버가 준비할 폴더

projects/<project>/
├── PROJECT.md                 # 목적·소유자·공개 범위·데이터 분류
├── ARCHITECTURE.md            # API/MCP·DB·외부 의존성 구조
├── OPERATIONS.md              # 실행·헬스체크·백업·중지 방법
├── Dockerfile                 # 이미지 빌드 정의
├── compose.member.yml         # 멤버 실행용 compose
├── deploy/
│   ├── service-request.yaml   # 서비스 등록이 필요할 때만
│   └── caddy-request.yaml     # 외부 경로가 필요할 때만
├── REQUEST/                   # 관리자에게 부탁할 일이 있을 때만
│   ├── README.md              # 요청 목록과 상태
│   └── YYYY-MM-DD-<주제>.md   # 요청 1건당 1개
├── mcp/                       # MCP 서버 코드와 README
├── rag/                       # 색인·검색 코드와 테스트
└── .dockerignore              # 빌드 컨텍스트 제외(.env·.git 등)

  • PROJECT.md에 적을 것

    프로젝트명·owner·목적·처리 데이터·민감정보 여부·private/public 구분·예상 사용자·삭제 정책

  • service-request.yaml에 적을 것

    서비스명·owner·이미지(digest 포함)·container port·loopback_port: admin-assigned(그대로 둠)·health 경로·외부 공개 여부·사유를 적습니다. 임시 서비스면 만료일(선택). CPU/RAM/PID 요구량은 이 파일이 아니라 OPERATIONS.md에 적습니다.

  • caddy-request.yaml에 적을 것

    hostname·path(/member/<ID>/로 시작)·loopback upstream(http://127.0.0.1:<포트>)·인증 방식·요청 사유·만료일(오늘 이후 날짜)을 적고, quota는 선택입니다. 값에 token·secret·password·private key 단어가 들어가면 검증이 거부합니다. health 경로는 service-request.yaml의 health_path에 적습니다.

  • REQUEST/에 적을 것

    관리자에게 부탁할 일이 있을 때만 REQUEST/README.md(요청 목록과 상태: 대기·전달됨·적용됨·거절)와 요청 1건당 문서 1개 REQUEST/YYYY-MM-DD-<주제>.md를 둡니다. 문서에는 무엇을·왜·필요한 것(host loopback 포트 배정은 «포트 배정 요청»으로)·만료 또는 삭제 기준·관련 파일·관리자 답변(날짜와 함께, 배정된 포트 포함)·상태를 적습니다. 요청은 관리자에게 별도 메시지로도 전달하고, 메시지에는 REQUEST/ 문서 경로만 알려 줍니다. secret·키·토큰·비밀번호·.env 값은 쓰지 않습니다. 예전처럼 프로젝트 루트에 REQUEST-*.md를 쓰던 경우에도 새 요청부터 REQUEST/에 쓰면 되고, 기존 문서는 편할 때 옮겨도 됩니다.

  • Agent에게 처음 보낼 문장

    이 프로젝트 폴더와 상위 운영 문서를 먼저 읽어라.
PROJECT.md, ARCHITECTURE.md, OPERATIONS.md를 작성하고
서비스 등록이 필요할 때만 deploy/service-request.yaml을 검토용으로 만들어라.
현재 SSH 계정 권한 밖의 작업, sudo, Caddy 수정, 중앙 서비스 변경은 하지 마라.
관리자에게 부탁할 일(DB·서비스 등록·인터넷 공개 등)이 있을 때만 REQUEST/YYYY-MM-DD-주제.md 로 요청 문서를 작성하라(비밀 값은 쓰지 마라).
누락된 요구사항·보안 위험·검증 결과를 README에 정리하라.

deploy/caddy-request.yaml — 외부 공개가 필요할 때만

# 필수(helper 검증): version request_id owner project hostname path upstream auth expires_at reason
version: "1"
request_id: <ID>-myservice-001
owner: <ID>
project: my-service
hostname: @@MCP_HOST@@
path: /member/<ID>/my-service
upstream: http://127.0.0.1:<배정포트>
auth: bearer
quota: application-enforced   # (선택) helper 는 읽지 않음 · 관리자 검토용
expires_at: <YYYY-MM-DD>
reason: canary 검증

예시의 <…>와 날짜는 실제 값으로 바꾸고, token·secret·password·private key 단어는 어느 값(reason 포함)에도 쓰지 않습니다. caddy 요청서는 제출 전에 @@PFX@@-caddy-request validate deploy/caddy-request.yaml로 형식을 확인합니다. path는 /member/<ID>/로 시작해야 하며, 관리자 전용 공개 경로는 이 요청서로 만들 수 없습니다.

현재 검증된 명령: @@PFX@@-member-setup과 @@PFX@@-project-build/up/status/logs/down은 staging 검증에서 통과했습니다. 멤버는 승인된 자기 프로젝트 범위에서만 실행하고, Caddy는 요청서 제출만 합니다. --apply는 관리자 import/reload gate 전까지 차단됩니다.

  • Paseo 직접 연결 암호 (파일 다운로드 켜기)

Paseo pairing URL을 가진 사람은 내 Agent를 조작할 수 있습니다. 비밀번호와 같게 취급하세요. 다시 필요할 때는 누구에게도 공유를 부탁하지 말고 @@PFX@@-paseo-pair로 직접 확인하세요.

비밀번호는 하나입니다

  • 초기 비밀번호

    6자리 초기 비밀번호는 개인 이메일로만 전달됩니다. 첫 SSH 로그인에서 즉시 변경하세요.

  • 변경 이후

    바꾼 비밀번호 하나를 SSH · Files · Windows 네트워크 드라이브에 공통으로 사용합니다. SSH에서 바꾸면 나머지도 자동으로 같은 값이 됩니다.

  • 네트워크 드라이브

    Windows 네트워크 드라이브는 SMB over QUIC로만 연결합니다. 다른 방식으로 열어 달라고 요청하지 마세요.

  • Paseo 직접 연결(선택)

    관리자에게 요청해 큰 파일(64MB 초과) 다운로드용 직접 연결을 켜면 데몬 암호를 따로 입력합니다. 계정 비밀번호와 같게 해도 되지만, SSH에서 바꿔도 자동으로 따라가지 않습니다.

서버에 등록하는 것은 하나뿐입니다.

  • SSH 공개키 (id_ed25519.pub — .pub으로 끝나는 파일)

쉽게 구분하는 법: 이름이 .pub으로 끝나면 남에게 줘도 되는 파일, .pub이 없으면 절대 주면 안 되는 파일입니다. 개인키가 유출된 것 같으면 새 키를 만들고 관리자에게 알리세요.
